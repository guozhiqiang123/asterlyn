# Architecture overview

## Architectural objective

The architecture must let Asterlyn grow from a Git workbench into a mature developer environment without placing every future capability in one process, one state store, or one framework.

```text
Presentation (TypeScript, CodeMirror, design system)
                         |
Versioned application commands and events
                         |
Application services (use cases, jobs, cancellation, policy)
                         |
Domain capabilities (Git, workspace, editor, language, debug, tasks)
                         |
Adapters (system Git, filesystem, LSP/DAP, terminal, OS keychain)

Tauri is a shell/transport adapter, not the domain center.
```

## Initial repository layout

- `crates/asterlyn-git`: pure Rust models, parsers, and safe system-Git invocation. It has no Tauri dependency.
- `crates/asterlyn-workspace`: pure Rust bounded text-file reads, revision checks, and durable replacement. It has no Git, Tauri, DOM, or CodeMirror dependency.
- `src-tauri`: desktop command registration and serialization boundary.
- `src`: frontend application state, views, and CodeMirror integration.
- Future capabilities become separate crates or supervised processes when their lifecycle, failure domain, or dependency weight justifies it.

## Dependency rules

1. Domain code cannot import Tauri, DOM, or CodeMirror types.
2. UI code consumes serializable application models and never parses raw Git porcelain.
3. All external process invocation uses argument arrays, never shell interpolation.
4. Mutation commands are narrower than query commands and return enough state for the UI to reconcile.
5. UI state is replaceable; repository truth is re-read from Git after mutations.
6. Long-running work supports cancellation, progress, bounded output, and stale-result rejection.
7. Branch mutations accept literal local refs or validated new names only. The UI waits for complete working-tree discovery, and the Git core independently rejects any staged, unstaged, conflicted, or untracked blocker immediately before invoking `git switch`.
8. Remote mutations accept configured remote names rather than URLs. U5 supports only the canonical branch mapping from `refs/heads/*` into `refs/remotes/<remote>/*`, disables implicit tag/submodule/signing/force expansion, and returns typed failure categories instead of child-process output.

## Runtime model

M1 uses the Tauri webview process plus a Rust host. Git operations run off the UI thread. Later language servers, debuggers, terminals, extension hosts, remote agents, and AI providers run behind supervisors with explicit lifecycle and resource budgets.

This avoids both extremes: a monolith that loads every subsystem at startup and microservices introduced before a process boundary has operational value.

## Evolution seams

- **Desktop shell:** the application protocol isolates Tauri-specific details. If operating-system webviews become a blocker, the shell can change without rewriting Git/domain code.
- **Workbench shell:** the activity rail, left tool dock, persistent editor host, and bottom tool dock are independent regions. Files and Changes share the left dock while Branches occupies the bottom dock, so tool visibility does not replace the active document. Each hideable dock has its own top-right Hide action in addition to the activity-rail toggle, and a dock header uses one primary title with its count adjacent. The project tree owns one explicit file-or-directory selection plus a set of expanded directory paths; locate, recursive expand, and recursive collapse mutate only that presentation state and never trigger Git mutation. Closed directories retain their in-memory nodes but do not mount descendant DOM until disclosure, and the pure tree projection is cached for one exact file/change/ignored snapshot. The Changes tool has independent row-selection and commit-inclusion state: row activation opens one complete local Diff, while checked file, directory, and group controls determine the exact commit set. Its tree/flat projection and directory disclosure are presentation state over the same changed-file identities. Pointer bursts are reduced to the latest value in each animation frame; an interactive resize writes only its affected layout property and coalesces editor measurement. Layout preferences are versioned and contain no repository truth; they include the selected-commit summary height and Changes commit-composer height, while each tree/flat changed-file projection is a separate preference over stable path selection.
- **Desktop chooser and windows:** project-folder selection is a presentation/platform concern behind the frontend bridge. The Tauri runtime may present a folder-only operating-system dialog and returns only the selected path; cancellation produces no state change. Every successful open creates an explicit active workspace plus an optional Git capability. Git is enabled only when the selected canonical folder is exactly the discovered worktree root; an ordinary folder, including a selected subdirectory inside a larger repository, never inherits ambient parent-repository authority. The first selection opens in the current empty window. Once that window owns a project, a different selection requires an explicit current-window or new-window choice. One Rust window factory creates both the initial shell and later project windows so dimensions, permissions, and platform chrome cannot drift: macOS keeps native decorations and traffic-light controls with an overlay title bar and hidden title, while Windows and Linux use the compact undecorated shell with custom controls on the right. A read-only chrome-mode command lets the frontend reserve the macOS control area and suppress duplicate custom controls; it carries no project state. New project windows consume one pending canonical path and receive an independent active-workspace authorization keyed by their Tauri window label. Destroying a window removes its authorization, pending path, and cancellable scan entries without affecting another project window. The shell grants both close-request and destroy capabilities to every project window: operating-system close requests may be prevented for dirty-buffer handling, while a confirmed clean/saved closure destroys the exact current window instead of recursively issuing another close request. Browser demo mode reports that native selection is unsupported and may expose a clearly labelled manual-path simulation. This capability does not belong to the Git domain and does not grant general filesystem access.
- **Editor engine:** CodeMirror is wrapped as an editor surface. Document models, commands, diagnostics, and navigation must not leak CodeMirror classes across the application boundary. Each bounded open text tab retains one editor state, parser tree, undo history, selection, and scroll offsets, while only the active tab mounts a view; activation reuses that state and never rebuilds the Files tree. Edit notifications are animation-frame-coalesced and exact line-ending metadata is updated incrementally, with synchronous flush before lifecycle operations. Basic syntax highlighting matches a bounded file's name inside that adapter, loads the catalog and selected parser on demand, rejects stale asynchronous completions, and retains plain-text editing on failure. Code folding belongs to the same syntax adapter: Lezer languages consume parser node ranges, while legacy Kotlin and Groovy modes receive a bounded token-aware brace service and XML receives a first-tag-line fold anchor. This Stage 3 path adds no repository index or language service. The read-only unified and split Diff adapters reuse the same loader and token theme rather than maintaining a second syntax system; none of these presentation paths is language intelligence. Markdown rendering is a separate presentation adapter: `markdown-it` is loaded only when a Markdown preview is requested, receives the current in-memory buffer, and cannot read or write workspace files.
- **Workspace files:** the workspace capability owns canonical-root activation, deterministic bounded file discovery, component-by-component non-link traversal, text decoding, content revisions, atomic replacement, bounded binary reads, and the private recovery-journal format. Ordinary folders use the explicit `workspace` file identity and revalidate it against a fresh catalog before every read or save. Git projects instead authorize a root-qualified identity against a fresh tracked-and-non-ignored-untracked catalog capped at 100,000 files. The Files tool may additionally request a separately bounded display-only list of Git-ignored files and collapsed directories for visual context. Those entries never enter read, save, search, or replacement authorization. Search and replacement retain their independent 5,000-candidate scan budget even though navigation and exact file authorization can see the larger catalog. Tauri supplies the application-local recovery directory, serializes workspace writes, translates identities, and rejects every Git command unless the active workspace explicitly owns Git capability; it cannot become the filesystem policy owner. Recovery blobs are bounded exact-byte safety data outside the project, never repository truth.
- **Image presentation:** raster preview is a bounded presentation adapter rather than an image-editing engine. Rust reads only a freshly authorized current project file or a freshly revalidated Git change/commit identity, identifies content from its signature, rejects animation, limits each encoded source to 16 MiB and 16 million decoded pixels, and limits a two-sided Diff to 24 million aggregate pixels. It then publishes a fixed media-type base64 data URL for the operating-system WebView to decode. Supported content is PNG, JPEG, static GIF, static WebP, BMP, and ICO. SVG is deliberately excluded because active or externally referenced content needs a separate sanitization and trust design. No decoder library, network fetch, temporary image file, or general blob/object-ID command is exposed. Working image Diff compares `HEAD` with the current worktree; commit image Diff uses the same first-parent/root-commit policy as text Diff.
- **Navigation and search:** file/command ranking and project-scoped recents remain pure presentation state over the bounded project catalog. Workspace text search is a lazy, cancellable application service that regenerates the active project's authorized candidate set—Git-qualified for an exact repository root, generic workspace-qualified otherwise—before delegating bounded literal or line-local regex matching and full-workspace-path include/exclude filtering to the workspace capability. Context previews and every option remain part of the stale-response identity. E2.3 replacement reruns that authorization, builds a separately bounded exact-byte plan, and publishes durable application-local recovery before using the E1 save path. It creates no startup index or parallel project database; active-buffer replacement remains CodeMirror-owned and undoable until explicitly saved.
- **Diff presentation:** Git returns one bounded canonical patch. Unified view displays it directly; split view derives aligned before/after documents in the presentation layer and synchronizes both scroll axes by source offset. Whitespace visibility is a CodeMirror decoration over the same patch, never a different Git query, so display preferences cannot alter review truth.
- **History presentation:** Git returns topologically ordered commits with every parent object ID. A pure frontend projection owns transient graph lanes, colors, fan-out, convergence, and accessible row summaries; it never derives ancestry from ref names, decorations, dates, or visual adjacency.
- **Git backend:** system Git is the M1 reference adapter. libgit2 or specialized readers may later accelerate selected read paths, but writes retain one canonical semantics until parity is proven.
- **Language adapters and intelligence:** Asterlyn owns a capability-oriented language adapter, not greenfield Kotlin or Groovy grammars. Stage 3 adapters may provide only syntax highlighting, folding, brackets, and indentation from lazy Lezer support or bounded legacy fallbacks. Later language packs may evaluate maintained upstream Tree-sitter grammars behind a lazy worker and map their trees into editor capabilities; only active documents retain incremental trees, and large files degrade explicitly. Completion, navigation, diagnostics, symbols, formatting, refactoring, LSP supervision, and repository indexing remain Stage 4 capabilities with independent lifecycle and resource gates. See [`ADR-0006`](decisions/0006-language-adapter-evolution.md).
- **Extensions:** internal capability boundaries mature before a public ABI. Public APIs are versioned and capability-scoped.
- **Persistence:** lightweight interface preferences use repository-independent versioned browser storage with strict choice validation and safe defaults. E3.1 persists application font size, editor font size, line height, letter spacing, inserted-space indent size, tab display width, Diff layout, and whitespace visibility; these values cannot rewrite repository or document truth. Successful project opens maintain one startup hint plus an eight-entry, deduplicated most-recently-used menu list. A missing or invalid startup project is removed from both stores and returns startup to the system folder chooser instead of becoming a fatal application state. Settings that lack a real service boundary, including localization, light/system themes, and per-language formatting, remain visibly marked as planned instead of storing inert values. Durable workspace metadata and future settings with migration requirements use atomic writes; a future SQLite store requires forward migrations, backups, and rollback evidence.

## State and event flow

The frontend requests an opened-project result with a monotonically increasing request generation. The backend returns a canonical workspace root and an optional immutable repository snapshot. Ordinary-folder refresh replaces only its bounded file catalog and preserves valid disclosure identities; its Git activity, remote action, bottom tool window, and Git commands remain disabled. Repository refresh is deliberately two-phase: tracked/index state, the bounded all-refs history, and ref state arrive first; an independently cancellable untracked-path scan completes the snapshot afterward. Refreshing the same root does not reuse the project-switch path: the existing project catalog remains visible while its replacement loads, valid path-keyed disclosure and selection identities survive, removed identities are pruned, and the current scroll offset is retained. The UI identifies pending untracked discovery instead of briefly claiming the repository is clean, merges a supplement only into its matching generation, and cancels obsolete Git child processes when the project changes or a mutation begins.

After a checked commit, tracked-file Revert, legacy stage/unstage command, or branch/remote mutation, the application requests fresh tracked state and starts a new untracked scan rather than manually pretending the mutation succeeded. Successful in-application text saves debounce into an active-window-authorized tracked-change query, merge only into the matching repository generation, and silently replace the retained untracked supplement; this updates Changes, project-tree colors, editor-tab colors, and working-Diff selection without rebuilding history, refs, catalogs, tree disclosure, or editor buffers. File-system events are coalesced and treated as refresh hints, not truth. The compatibility `snapshot` operation in the pure Git crate still composes both phases for callers that require an atomic-looking complete result, while interactive callers use the phased API.

Checked commit is a typed top-level-repository transaction, not a sequence of frontend stage commands. The request carries the last-observed complete `FileChange` identities. Under one canonical-root mutation lock, the Git boundary repeats full status, rejects stale identities, repository operations, conflicts, and submodule entries, and invokes Git with literal pathspecs plus `commit --only`. The new commit therefore contains the selected files' current worktree content while unrelated staged index entries remain staged. Selected untracked files receive only temporary intent-to-add entries; an ordinary hook or command failure with unchanged `HEAD` removes just those introduced entries. After Git returns successfully, Asterlyn verifies the observed commit parent and changed-path allowlist before publishing an object ID. If an external Git process changes `HEAD` during the transaction, Asterlyn never rolls that ref back: a rejected Git command fails with a refresh-and-inspect requirement, while a successful but unverifiable command returns no object ID and a do-not-retry warning. A successful commit whose following refresh fails is likewise reported as successful with a refresh warning. Local and remote writes share the same process-local per-root lock; external Git concurrency is handled by the non-rollback outcome rather than assumed away.

Changes Revert is deliberately narrower than general discard/reset support. It acts only on the explicitly selected row after confirmation, repeats exact status validation, refuses an unborn branch, conflicts, submodules, untracked paths, and index-added/copied paths, and restores supported tracked paths from `HEAD` in both index and worktree. Dirty open editor buffers block the action. Deleting untracked files, cleaning directories, arbitrary reset, and conflict resolution remain separate future capabilities with their own preview and recovery requirements.

Remote work follows the same reconciliation rule but uses a repository-scoped cancellable operation. Fetch updates only the selected remote's canonical branch-tracking namespace and does not prune in the initial slice. Pull performs that bounded fetch, then revalidates `HEAD`, upstream configuration, repository-operation state, and complete cleanliness before a fast-forward-only merge to the fetched commit ID. Push sends the current full local ref to the exact configured upstream ref, or publishes the same-named branch to an explicitly selected remote; it cannot force, mirror, follow tags, sign, or recurse into submodules. Cancellation terminates the matching Git process tree and never attempts rollback. A cancelled push has an explicitly unknown remote outcome until a later fetch reconciles it.

Commit inspection is a separate, lazy read path rather than part of the repository snapshot. A selected commit first loads its NUL-delimited changed-file summary and then loads only the selected file patch. The frontend may project those files as a directory tree or a path-sorted flat list, but both modes preserve one repository-relative path selection and dispatch the same typed Diff document. Commit decorations are matched against the current ref snapshot for semantic presentation; unknown decoration types remain visibly neutral rather than being inferred from their names. Ordinary and merge commits are compared with their first parent, matching the mainline review model used by common Git clients; root commits are compared with the empty tree. The frontend rejects responses whose commit or file selection is no longer current, while the Rust boundary accepts only full hexadecimal object IDs and repository-relative paths.

The snapshot's default history is the deduplicated set reachable from the exact object IDs observed for local branches, remote-tracking branches, tags, and a detached `HEAD`. Passing observed IDs rather than open-ended revision expressions keeps the graph aligned with the snapshot's ref set. Git orders the bounded result topologically, and the frontend projects only the reported parent IDs into lanes. Non-commit refs do not create commits or fabricated edges.

Selecting one displayed ref uses a separate lazy read path. Both the left branch navigation and the compact toolbar Branch shortcut are logical at the workspace level: they render one item per ref kind and complete ref name among the currently included Git roots, preserve every catalogued root match in selection state, and issue the same query against the roots enabled by the Paths control. The advanced selector retains exact root-qualified multi-ref control. A logical item that maps to more than one root is history-only and cannot expose a single-repository mutation inspector. The Rust boundary accepts only complete literal refs paired with their owning root, verifies each one, resolves it to a commit object, and queries the resulting object IDs with an explicit path separator and the same topological ordering. Activating the selected logical ref again restores the snapshot's all-refs history. The frontend rejects responses whose request generation, repository root, or selected ref no longer matches. Collapsing a ref group is presentation state only and cannot alter the selected ref, history data, repository truth, or active editor document.

Workbench state is orthogonal to optional Git state. Each native window owns one transient workspace/workbench/editor session, while project-independent preferences and recent-project hints remain shared profile data. A typed editor-document descriptor selects welcome, project-file, project-image, working-diff, or commit-diff content independently of left and bottom tool visibility. Views dispatch identifiers into the application state flow and never manipulate another zone's DOM or editor instance. Pointer and keyboard splitter actions update only validated layout dimensions; they do not trigger Git work. The Files view projects the bounded authorized file catalog together with separately typed ignored display entries and current change status when Git exists. Selection, disclosure, locate, and recursive expand/collapse remain frontend state; opening a file or image still crosses the fresh Stage 3 authorization boundary.

Stage 3 text editing introduces a transient editor session rather than replacing repository state. Persistent text tabs own exact root-qualified file identities, the current exact content, the last successfully loaded-or-saved content baseline, independently versioned buffers, load epochs, and at most one save request; a single replaceable Diff preview remains read-only. Dirty state is content identity against that baseline rather than edit-event count, so undoing exactly to the baseline becomes clean while a save completion advances only to the content captured by that save and cannot erase newer edits. A repository refresh preserves text tabs and dirty buffers. Tab close, repository switch, and window close cannot remove dirty content without a successful save. Read and save responses are accepted only when workspace identity, tab identity, request epoch, and save request ID still match. The first slice persists no drafts, so it intentionally offers no discard or force-save action.

The editor tab strip is the ordinary text editor's only top metadata row. It uses current Git snapshot status tokens for file labels, keeps one fixed open-document menu outside the horizontally scrolling tab viewport, and scrolls the selected tab into view without changing editor ownership. Current text encoding is derived from the active loaded text tab and appears in the shared bottom status bar; Diff-only controls retain a separate contextual toolbar because they change the Diff projection rather than the file buffer. The open-document menu and scroll position remain transient presentation state.

Each Markdown text tab additionally owns one transient `source | split | preview` presentation choice. Source and split mount the same editable buffer adapter; preview removes only the widget while retaining exact session content and dirty/save state. Split presentation owns one disposable, keyboard-operable divider and a shared transient source-width ratio, not an E3.2 editor group. Its source and preview viewports link bidirectionally by normalized vertical progress while retaining independent horizontal offsets; this intentionally avoids claiming exact source/rendered block correspondence. Preview requests are coalesced, carry an in-memory request generation, and may update only the currently active matching text tab. The renderer escapes raw HTML, replaces images with non-fetching placeholders, and projects links as non-navigating text. Live rendering is bounded to 512 KiB while the existing two-MiB source-editing limit remains unchanged.

E2 navigation adds a separate transient command-surface state rather than overloading editor tabs or optional Git state. Quick-open and recent-file activation dispatch exact project-file identities through the existing text-tab flow. Workspace search owns one cancellable request at a time and accepts results only when the request identity and project generation remain current. Result locations are applied after the target tab's matching load epoch succeeds, so late search or file-read responses cannot move a newer editor selection.

## Failure policy

- A failed Git command returns its operation, exit status, and sanitized stderr.
- A failed remote command returns only a typed authentication, network, rejection, or unknown category; bounded child output is discarded and remote URLs never enter application state.
- Remote credentials remain inside configured non-interactive Git credential helpers or the SSH agent. Asterlyn disables terminal/askpass interaction and inherited Git tracing for these commands and never stores a username, password, token, or authorization header.
- Unsupported repository states remain visible; they are not normalized into “clean.”
- Invalid UTF-8 is decoded lossily for display while raw paths remain an acknowledged M1 limitation.
- Crashes in optional services must not bring down the editor host.
- Any feature that can rewrite or discard work needs a preview and recovery story before release.
