# M1 baseline — 2026-09-08

## Purpose

This is the first evidence set for the Git GUI First vertical slice. It establishes an honest starting point; it is not a claim that M1 is complete or optimized.

## Comparison context

- **Asterlyn source:** commit `1b26255` plus the benchmark-only `asterlyn-git/examples/inspect.rs` file that does not enter the desktop binary.
- **Machine:** Deepin 23.1 x86_64, DDE/X11, AMD Ryzen 5 3600X (6 cores/12 threads), 20,425,524 KiB RAM.
- **Toolchain:** Git 2.47.2, Rust 1.98.1, Node.js 24.19.0, Tauri 2.11.5, WebKitGTK 2.46.3.
- **Build:** Tauri release profile; frontend production build with source maps; native packages unsigned.
- **Clean fixture:** newly initialized empty repository with no commits or changes.
- **Large fixture:** local Rebased checkout at `2896562e69ff2cac3c90eb3aae4bcce0d4aa9a99`, 273,559 tracked paths, four visible working-tree entries, and no Asterlyn mutations.
- **Linux rendering:** software compositing on Deepin because the installed WebKitGTK package failed `DRM_IOCTL_MODE_CREATE_DUMB` in the measured session. Asterlyn now selects this compatibility path automatically on Deepin.

## Functional and build evidence

- TypeScript strict check: passed.
- Vite production build: passed; JavaScript 277.87 kB raw / 88.36 kB gzip; CSS 16.61 kB raw / 4.36 kB gzip.
- Rust workspace tests: 8 passed (7 Git core/parser/integration tests and 1 Deepin compatibility test).
- Rust workspace Clippy with warnings denied: passed.
- Browser workflow smoke test: changes/history/branches navigation, per-path stage, commit-button state, demo commit, and post-commit history update passed; no console warnings/errors.
- Native smoke test: release binary opened the real Rebased checkout, rendered its four changes, and displayed a selected textual patch. No write action was invoked.
- Tauri environment check: all prerequisites passed through the user-local sysroot.
- Native packaging: `.deb`, `.rpm`, and AppImage all succeeded. AppImage library collection took roughly two minutes on this host and is a packaging-speed concern.

## Git-core latency

The release-mode inspection utility loaded a complete snapshot ten times. Each snapshot includes branch headers, all tracked and untracked status, 150 commits, and local/remote refs.

| Fixture | Minimum | Median | p95 / maximum | Sample diff |
| --- | ---: | ---: | ---: | ---: |
| Empty repository | 2.455 ms | 2.576 ms | 3.187 ms | n/a |
| Rebased, 273,559 tracked paths | 1,126.012 ms | 1,145.474 ms | 1,156.624 ms | 75.203 ms / 972 bytes |

An isolated command comparison on Rebased showed why the full refresh is slow:

| Status mode | Observed range |
| --- | ---: |
| porcelain v2 with all untracked paths | 1,095–1,153 ms |
| porcelain v2 with rename detection disabled | 1,099–1,109 ms |
| porcelain v2 with untracked scanning disabled | 186–262 ms |

**Interpretation:** regressed against the provisional ordinary-refresh budget. The bottleneck is untracked-file discovery in system Git for this very large checkout, not commit/ref parsing and not rename detection. The next design should return tracked state first (approximately 0.2 seconds here), then merge an asynchronous, cancellable untracked scan. Existing Git untracked-cache/fsmonitor configuration may be used when present, but Asterlyn must not silently alter a user's repository configuration.

## Startup and steady state

Five warm launches against Rebased created a visible native window in 129, 160, 162, 143, and 148 ms (median 148 ms, maximum 162 ms). This measures native-window visibility, not repository-data readiness. Direct screenshot polling introduced too much observer overhead for an exact meaningful-paint number, so repository readiness is conservatively represented by the independent snapshot measurement above rather than reported as false precision.

Memory was measured from `/proc/<pid>/smaps_rollup` after approximately 60 seconds, summing the Asterlyn host, WebKit network process, and WebKit web process. PSS is the acceptance metric; summed RSS is included because it is widely recognized but double-counts shared pages.

| Loaded state | Process-tree PSS | Summed RSS | 10-second idle CPU |
| --- | ---: | ---: | ---: |
| Empty repository | 198.56 MiB | 426.88 MiB | 0.10% |
| Rebased checkout | 210.87 MiB | 441.11 MiB | 0.30% |

Loading Rebased added about 12.31 MiB PSS (+6.2%) over the clean fixture. The 210.87 MiB result is under the provisional 220 MiB Linux budget, but by only 9.13 MiB; one run is insufficient to call that budget secure.

## Conclusion

**Mixed.** The architecture and first workflow are viable, the frontend/native/package builds succeed, the empty-repository core is effectively instantaneous, window creation is fast, idle CPU is low, and the measured PSS narrowly meets the first budget. Full refresh on a 273k-path repository misses the latency budget because untracked discovery is synchronous, and the memory margin is too narrow to absorb future editor/language capabilities without active resource governance.

## Limitations

- One Linux machine and one large repository; no Windows/macOS data yet.
- One steady-state memory sample per loaded state; no confidence interval or repeated cold-boot runs.
- The large fixture was dirty and its untracked set can change over time.
- Startup paint was observed visually, but only window-visibility timing is accepted as numeric evidence.
- Browser demo mutation validates UI state flow, while native Git mutations were validated only in temporary repositories.
- Packages are unsigned and were not installed system-wide.

## Next action

Before expanding M1 breadth, implement a two-phase refresh contract (tracked snapshot first, untracked scan second), measure repeated process-tree PSS, and add a native UI automation path against a temporary repository. Keep CodeMirror lazy-loading and process isolation on the Stage 3 agenda so the current memory headroom is not consumed accidentally.
